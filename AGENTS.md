# AGENTS.md — Правила разработки Frontend

Этот документ определяет общие правила разработки для всех frontend-проектов.

Главная задача — писать простой, понятный, поддерживаемый код, который соответствует существующей архитектуре проекта.

## 1. Приоритеты

При разработке соблюдать следующий порядок приоритетов:

1. Корректность работы приложения и сохранение существующего поведения.
2. Существующая архитектура и соглашения проекта.
3. Настройки TypeScript, ESLint, Prettier и других инструментов.
4. Правила этого документа.
5. Личные предпочтения при реализации.

Если правила противоречат существующей реализации или настройкам проекта, сначала изучить причину и придерживаться фактических соглашений проекта.

## 2. Технологический стек

Основной стек:

| Область       | Технологии                                             |
| ------------- | ------------------------------------------------------ |
| UI            | Vue 3, Single File Components                          |
| Язык          | TypeScript                                             |
| Сборка        | Vite                                                   |
| Стили         | Tailwind CSS                                           |
| UI-библиотека | Naive UI                                               |
| Роутинг       | Vue Router                                             |
| Состояние     | Pinia, Pinia Colada или существующие composable stores |
| HTTP          | Axios                                                  |
| Иконки        | Iconify                                                |

Дополнительные библиотеки и инструменты могут отличаться между проектами.

Перед использованием новой библиотеки проверить, нет ли уже подходящего решения в проекте или текущем стеке.

Не добавлять зависимости без реальной необходимости.

## 3. Основные принципы

### 3.1. KISS

Предпочитать самое простое решение, которое полностью решает задачу.

- Не создавать абстракции на будущее без конкретной необходимости.
- Не создавать фабрики, классы и composables ради нескольких строк кода.
- Не обобщать код, который пока используется только в одном месте.
- Не дробить простой код на множество файлов и функций.
- Не создавать дополнительные уровни архитектуры без необходимости.
- Не добавлять универсальность, если она усложняет текущую реализацию.
- Не использовать сложные паттерны там, где достаточно обычной функции или объекта.

Если задачу можно решить простым способом средствами Vue и TypeScript, не нужно придумывать дополнительную архитектуру.

### 3.2. Читаемость

Код должен быть понятен разработчику, который впервые открыл файл.

- Использовать понятные названия переменных и функций.
- Не сокращать названия без необходимости.
- Разбивать сложные выражения на отдельные переменные.
- Не использовать вложенные тернарные операторы.
- Не писать сложную логику непосредственно в template.
- Предпочитать явные условия неочевидным конструкциям.
- Не объединять несколько независимых действий в одну перегруженную функцию.

### 3.3. Согласованность

- Следовать существующему стилю проекта.
- Использовать уже существующие компоненты, composables, типы и сервисы.
- Не создавать альтернативную реализацию уже существующего решения.
- Не менять соглашения проекта в рамках обычной задачи.
- Не смешивать разные подходы к решению одной задачи без необходимости.

### 3.4. Минимальные изменения

При работе с существующим кодом:

- Сначала изучить текущую реализацию и связанные с ней файлы.
- Изменять только то, что необходимо для выполнения задачи.
- Не переписывать работающий код ради личных предпочтений.
- Не выполнять массовый рефакторинг без запроса.
- Не менять публичные контракты без необходимости.
- Не исправлять посторонние проблемы, не связанные с задачей.
- Не форматировать целые файлы без необходимости.
- Не удалять существующую функциональность без понимания её назначения.

## 4. Анализ перед реализацией

Перед написанием кода:

1. Изучить существующую реализацию.
2. Найти связанные компоненты, composables, типы и API.
3. Проверить, какие решения уже используются в проекте.
4. Убедиться, что необходимые методы и свойства действительно существуют.
5. Определить минимальный набор изменений.

Не предполагать существование функций, типов, API и возможностей библиотек.

Если поведение библиотеки неизвестно, проверить её фактическую типизацию или документацию.

Не придумывать методы и свойства сторонних библиотек.

Если задача затрагивает архитектуру, публичные контракты или несколько независимых модулей, сначала объяснить предполагаемый подход.

## 5. TypeScript

Использовать TypeScript с сохранением строгой типизации.

### Общие правила

- Не использовать `any`.
- Для неизвестных значений использовать `unknown` с последующей проверкой типа.
- Не отключать проверки TypeScript ради быстрого исправления ошибки.
- Не использовать `@ts-ignore`.
- `@ts-expect-error` допустим только с объяснением причины.
- Не дублировать уже существующие типы.
- Использовать utility types: `Pick`, `Omit`, `Partial`, `Required`, `Record` и другие, когда это упрощает типизацию.
- Не использовать приведения типов `as` без необходимости.
- Не создавать сложные generic-типы, если достаточно обычного типа.
- Не использовать `enum`, если достаточно union type или объекта `as const`.

### Типы и интерфейсы

Использовать `type` для:

- Union и intersection типов.
- Примитивных алиасов.
- Tuple.
- Типов функций.
- Составных типов через utility types.

Использовать `interface` для объектных контрактов, которые предполагается расширять.

Не создавать отдельный тип для каждого локального объекта, если его структура проста и используется только один раз.

### Типизация функций

Указывать типы аргументов и результата, когда это улучшает читаемость или необходимо для публичного контракта.

Не дублировать тип результата, который TypeScript однозначно выводит из реализации.

## 6. Vue 3

### 6.1. Общие правила

- Использовать Composition API.
- Для новых компонентов использовать `<script setup lang="ts">`.
- Использовать Single File Components.
- Предпочитать стандартные возможности Vue дополнительным библиотекам.
- Не переносить локальное состояние компонента в глобальный store без необходимости.
- Не дублировать состояние, которое можно получить через `computed`.
- Не изменять props напрямую.
- Не создавать лишние watchers.

### 6.2. Реактивность

Использовать:

- `ref` для простого реактивного состояния.
- `reactive` для объектов, когда это действительно удобно.
- `computed` для производных значений.
- `watch` и `watchEffect` для побочных эффектов и синхронизации.

Не использовать `watch`, если задачу можно решить через `computed`.

Не создавать отдельный `ref`, если его значение полностью зависит от другого реактивного значения.

### 6.3. Компоненты

- Props должны иметь понятные и типизированные контракты.
- Emits должны быть типизированы.
- Использовать `defineModel`, если это упрощает двустороннюю привязку.
- Не создавать props и emits без необходимости.
- Не передавать компоненту данные, которые он может получить из уже доступного контекста без нарушения архитектуры.
- Не помещать бизнес-логику в компоненты отображения.
- Не создавать компонент ради одного простого HTML-элемента.

Компонент должен отвечать за отображение и взаимодействие с пользователем, а не за всю бизнес-логику приложения.

### 6.4. Template

- Использовать понятную структуру разметки.
- Не размещать сложные выражения в атрибутах.
- Не вызывать несколько независимых действий непосредственно в обработчике события.
- Для `v-for` всегда указывать стабильный `:key`.
- Не использовать индекс массива в качестве ключа, если есть стабильный идентификатор.
- Не совмещать `v-if` и `v-for` на одном элементе.
- Использовать семантические HTML-элементы.
- Для интерактивных элементов предусматривать доступное имя.

Vue 3 поддерживает несколько корневых элементов в template. Не добавлять лишний wrapper только ради одного корневого элемента.

`v-if` и `v-show` выбирать исходя из задачи: частоты переключения и стоимости создания содержимого.

### 6.5. Lifecycle и ресурсы

Все созданные ресурсы должны корректно освобождаться:

- Event listeners.
- Timers.
- WebSocket-подключения.
- Подписки.
- Observer.
- Canvas и другие внешние экземпляры.
- Временные DOM-обработчики.

Использовать соответствующие lifecycle hooks для очистки.

## 7. Компоненты и composables

### Компоненты

Перед созданием нового компонента проверить, нет ли подходящего в проекте.

Общие UI-компоненты должны решать конкретные повторяющиеся задачи.

Не создавать универсальный компонент с большим количеством props и условий, если несколько простых компонентов будут понятнее.

### Composables

Composable должен содержать переиспользуемую реактивную логику.

- Называть composables с префиксом `use`.
- Возвращать только необходимые наружу значения и функции.
- Не скрывать побочные эффекты за неочевидными названиями.
- Не создавать composable для простой функции без реактивности.
- Не выносить логику из компонента только ради сокращения размера файла.
- Следить за очисткой ресурсов и подписок.

Чистые функции размещать в обычных утилитах, а не превращать их в composables.

## 8. Состояние приложения

Использовать существующий подход к управлению состоянием проекта.

- Локальное состояние хранить внутри компонента.
- Состояние нескольких компонентов одной функциональной области размещать в соответствующем store или composable.
- Общее состояние приложения размещать в глобальном store.
- Не хранить в глобальном состоянии данные, которые нужны только одному компоненту.
- Не создавать несколько источников истины для одних и тех же данных.
- Не дублировать серверное состояние без необходимости.
- Для производных значений использовать computed.

Не смешивать Pinia, composable stores и другие подходы без архитектурной причины.

## 9. API и асинхронные операции

- Использовать существующий HTTP-клиент.
- Не создавать отдельный Axios instance для каждого API-модуля без необходимости.
- API-запросы размещать в соответствующем слое проекта.
- Не выполнять HTTP-запросы непосредственно в шаблоне.
- Использовать существующие типы API.
- Не дублировать модели сервера вручную.
- Обрабатывать ошибки явно.
- Не скрывать ошибки пустым `catch`.
- Не показывать пользователю технические сообщения и stack trace.
- Не создавать несколько независимых loading-состояний для одной операции.
- Предусматривать состояния загрузки, ошибки и пустого результата там, где они необходимы.

Для повторяющихся запросов использовать существующие composables или механизмы управления серверным состоянием.

Не создавать собственную систему запросов, если проект уже использует готовое решение.

## 10. Стили и UI

### 10.1. Tailwind CSS

Использовать Tailwind для:

- Layout.
- Flex и Grid.
- Отступов.
- Размеров.
- Типографики.
- Простых состояний.
- Адаптивности.

Не создавать отдельный CSS-класс, если его можно понятно выразить несколькими utility-классами.

При этом не превращать разметку в нечитаемую последовательность из десятков классов. Сложные и повторяющиеся стили лучше вынести.

### 10.2. CSS

Использовать scoped CSS для локальных стилей компонента.

Обычный CSS предпочтительнее сложных и нечитаемых Tailwind-селекторов.

Статические стили размещать в Tailwind или CSS.

` :style` допустим для динамических значений: координат, размеров, вычисляемых цветов и других значений времени выполнения.

Не добавлять случайные цвета и размеры, если в проекте уже есть дизайн-токены.

### 10.3. UI-библиотеки

Если проект использует Naive UI или другую UI-библиотеку:

- В первую очередь использовать её готовые компоненты.
- Не создавать собственную замену существующему компоненту без необходимости.
- Использовать предусмотренные API для настройки темы и внешнего вида.
- Не переопределять внутренние стили библиотеки глобально без причины.
- Не добавлять дополнительные UI-библиотеки для решения уже закрытых задач.

### 10.4. Состояния интерфейса

Для интерактивных элементов учитывать:

- Loading.
- Disabled.
- Error.
- Empty.
- Success.

Не добавлять состояния и элементы интерфейса, которые не нужны конкретному сценарию.

Соблюдать доступность: подписи, фокус, клавиатурная навигация и семантика элементов.

## 11. Производительность

Не оптимизировать код преждевременно.

Сначала обеспечить корректность и понятность реализации.

Учитывать производительность, когда задача действительно этого требует:

- Большие списки и таблицы.
- Частые реактивные обновления.
- Тяжелые вычисления.
- Большие изображения.
- Canvas и WebSocket.
- Большие компоненты и маршруты.

Использовать lazy loading, виртуализацию и мемоизацию по необходимости.

Не добавлять `computed`, `shallowRef`, `markRaw`, `v-memo` и другие оптимизации без понимания их пользы в конкретной ситуации.

Не выполнять тяжелые вычисления непосредственно в template.

## 12. Именование и структура кода

### Именование

- Переменные и функции: `camelCase`.
- Компоненты, классы, типы и интерфейсы: `PascalCase`.
- Константы конфигурации: `UPPER_SNAKE_CASE`, если это соответствует существующему стилю.
- Composables: `useSomething`.
- Булевы значения: `is`, `has`, `can`, `should`, `show` или другое понятное смыслу имя.

Названия должны отражать назначение сущности.

Предпочитать `character`, `lobby`, `scene`, `message` вместо абстрактных `item`, `data`, `obj`, если контекст позволяет использовать более точное название.

### Структура файлов

- Не создавать файлы ради нескольких строк кода без необходимости.
- Не размещать всю логику приложения в одном файле.
- Группировать код по функциональности.
- Не смешивать UI, API и бизнес-логику без причины.
- Следовать существующей структуре каталогов проекта.
- Не переносить файлы между каталогами в рамках несвязанной задачи.

## 13. Форматирование

Форматирование должно соответствовать настройкам проекта и конфигурации ESLint/Prettier.

Если настройки не определяют форматирование явно, использовать следующие предпочтения:

- 1 таб для отступов.
- Двойные кавычки.
- Пустые строки между независимыми объявлениями переменных и функций.
- Группировать импорты по источнику.
- Использовать `import type` для импорта только типов.
- Не оставлять неиспользуемый код и импорты.
- Разбивать длинные и сложные выражения на несколько строк.

Не менять настройки форматирования проекта без отдельной задачи.

## 14. Работа с ошибками

- Не игнорировать ошибки TypeScript.
- Не отключать ESLint-правила без необходимости.
- Не использовать `as any` для обхода типизации.
- Не подавлять исключения пустым `catch`.
- Не заменять ошибку значением по умолчанию, если это скрывает проблему.
- Не добавлять проверки, которые не имеют смысла для конкретного контракта.

Обработка ошибок должна соответствовать уровню, на котором они возникают.

API-слой отвечает за обработку технических ошибок, UI — за корректное отображение результата пользователю.

## 15. Работа с существующими библиотеками

Перед использованием сторонней библиотеки:

1. Проверить, установлена ли она в проекте.
2. Изучить её существующее использование.
3. Проверить доступные типы и сигнатуры методов.
4. Использовать официальный API библиотеки.
5. Не обращаться к внутренним свойствам и методам без необходимости.

Не придумывать API библиотеки и не переносить поведение из другой версии.

Не устанавливать новую библиотеку, если задача решается существующими средствами.

## 16. Проверка результата

В этом проекте не добавлять и не запускать автоматические тесты без прямого запроса пользователя. Для проверки использовать TypeScript, ESLint, сборку и просмотр изменений.

После реализации:

1. Проверить изменённый код на очевидные ошибки.
2. Запустить доступную проверку TypeScript.
3. Запустить ESLint, если он настроен.
4. Запустить сборку, если это возможно.
5. Проверить итоговый diff.

Не заявлять об успешной проверке, если команда фактически не запускалась.

Если проверку невозможно выполнить, явно указать причину.

Не исправлять несвязанные ошибки, обнаруженные во время проверки, без необходимости.

## 17. Правила работы ИИ-агента

При выполнении любой задачи:

- Не переписывать код целиком, если достаточно локального изменения.
- Не создавать лишние файлы, типы, функции и абстракции.
- Не менять архитектуру без необходимости.
- Не добавлять зависимости без обоснования.
- Не дублировать существующие решения.
- Не выдумывать API и возможности библиотек.
- Не удалять код, назначение которого неизвестно.
- Не выполнять несвязанный рефакторинг.
- Не менять форматирование всего файла без необходимости.
- Не добавлять комментарии, которые просто пересказывают код.
- Не оставлять временные решения и закомментированный старый код.

Если задача понятна — сразу приступать к реализации.

Если есть несколько вариантов, выбирать самый простой, который соответствует архитектуре проекта.

Если есть существенная неоднозначность, влияющая на архитектуру или поведение приложения, сначала задать вопрос.

### Итоговый принцип

**Простой код лучше сложного. Понятный код лучше универсального. Существующее рабочее решение лучше новой абстракции без необходимости.**
