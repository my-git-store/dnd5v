# Lessons learned для dnd5v

Этот файл нужно прочитать перед любой работой в `dnd5v`. Он фиксирует решения, которые уже защищают данные и UI, а также типовые причины регрессий. Правила ниже важнее удобного краткого решения, если они явно не отменены задачей.

## 1. Архитектура

### Что уже сделано правильно

- Vue 3 + Composition API + TypeScript + Vite и существующий UI kit — базовый стек проекта. Новая система UI или второй frontend не нужны.
- Character v3 — каноническая сохранённая модель. Vue продолжает получать совместимую v2-проекцию через `CharacterSheetAdapter`; это позволяет развивать модель без переписывания всех компонентов.
- `useCharacterSheet` владеет draft, saved snapshot, dirty/loading/error/save state. Компоненты получают typed props и отправляют события.
- Domain helpers — чистые функции. Они считают derived values, не меняют Character и не хранят вторую копию истины.
- Migration и storage отделены от UI. Старые записи проходят через adapter и остаются читаемыми.
- Существующие модальные компоненты (`CModal`, `CModalRender`, `useDialog`) уже покрывают подтверждения и редакторы. Их нужно переиспользовать.

### Что нельзя ломать

- Не заменять adapter прямым доступом компонентов к `localStorage`, API или mock loader.
- Не переписывать v2-проекцию и не превращать `identity.class` из совместимой строки в обязательный объект без отдельной версии схемы.
- Не хранить модификаторы, итоговые бонусы, remaining spell slots или другие вычисляемые поля как независимый источник данных.
- Не менять backend, `my-table`, `Nastolka_backend`, legacy API или `nastolka-sheet-dnd5` в рамках задачи dnd5v.
- Не удалять старые storage keys, неизвестные поля и ручные значения при миграции.
- Не добавлять новый роут для сценария, который принадлежит текущему листу; создание персонажа остаётся вкладкой/контейнером корневого листа.
- Не дублировать один и тот же summary в нескольких местах без единого источника. Если значение уже живёт в header, второй редактируемый блок должен быть модальным или ссылаться на тот же draft.

### Рабочие паттерны

- Для нового поля сначала определить каноническое место в v3, затем adapter mapping, validation, UI projection и тест round-trip.
- Для изменения одного раздела делать малый вертикальный срез: типы → domain/миграция → adapter/composable → компонент → стили → тесты.
- Поля, которые могут отсутствовать в старых данных, добавлять optional с безопасным default и сохранять прежнюю семантику.
- Фильтры и поиск должны возвращать представление, не мутируя исходные массивы.
- Редакторы работают с локальной копией; отмена выбрасывает её, а общий Save записывает draft.

## 2. Ошибки и исправления

| Наблюдение | Причина | Правило на будущее |
|---|---|---|
| Повторный выбор расы/подрасы удваивал бонусы | Новое применение строилось от уже изменённых итогов | Хранить `creation.baseAbilityScores` и каждый раз пересобирать эффекты от базы и текущих источников |
| После смены класса оставались старые владения, языки или spellcasting | Владение было только display-строкой, без происхождения | Хранить `proficiencySources` и metadata для `race`, `class`, `background`, `manual`; удалять только источник, который заменяется |
| Старый v3 мог ломаться на неполной metadata | Миграция считала новые поля обязательными | Неполную optional metadata игнорировать с безопасным fallback; повреждённый JSON не подменять mock-defaults |
| Миграция рисковала потерять данные | Старый JSON рассматривался как материал для перезаписи | Делать независимую idempotent v3-копию, оставлять v1/v2 keys и сохранять unknown root/nested fields в `extensions` или копии записи |
| Ручные навыки/атаки могли быть приняты за D&D-формулу | Legacy `value` и `attackBonus` уже имели пользовательский смысл | Для legacy использовать `manual`; свободный `attackBonus: string` не парсить задним числом |
| В UI появлялись дубли и смещения | Функциональный и визуальный этапы смешивали ответственность | Сначала определить единый владелец значения и layout; не добавлять вторую копию summary или скрытую автоматизацию |
| Подтверждения были браузерными `window.confirm` | Не использовалась существующая modal-система | Для удаления и редактирования использовать `CModalRender`/`useDialog`, сохраняя keyboard/focus поведение |
| Кнопки и итоговые badges меняли позицию при раскрытии | Потоковый layout зависел от появившегося текста | Закреплять grid-области/колонки для action, source и total; проверять длинные подписи и оба состояния до/после открытия |
| Выбор навыка с checkbox был неочевиден | Управление и выбранное состояние были разнесены | Для выбора использовать кликабельную строку/карточку, явное selected-состояние и крупную галочку; повторный клик снимает выбор |
| Визуальные правки могли скрыть ошибки | Проверялась только сборка или только один viewport | Для UI проверять 1440, 1024, 430 и 375 px, focus/keyboard, empty/error/saved/dirty состояния; отделять runtime smoke от статической CSS-проверки |
| Полный test run иногда содержит старые падения | Ошибка окружения или baseline смешивается с изменённым scope | Записывать точный набор проверок и отличать новые падения от pre-existing; не чинить несвязанный код ради зелёного отчёта |

## 3. Правила данных

- **Версии и миграция.** Читать v3 → v2 → v1; promotion старой записи пишет только v3-копию. Миграция чистая, идемпотентная, не меняет исходный ключ и не удаляет его.
- **Совместимость.** Новые поля optional, defaults явные, старый payload валиден. Обязательное изменение смысла требует schemaVersion и отдельного мигратора, а не тихого преобразования в adapter.
- **IDs и embedded data.** Для классов, рас, spells, feats, features и equipment использовать стабильные IDs как ссылки на каталог. В Character хранить выбранные IDs и пользовательские поля; embedded snapshot допустим только для legacy/custom данных и должен сохраняться при round-trip.
- **Неизвестные поля.** До утверждения compatibility policy неизвестные root и nested поля нельзя выбрасывать. Сохранять их в `extensions` или object copy и валидировать только известную часть.
- **Raw и derived.** Сохранять raw scores, `max/used`, ручной текст и выбранный режим расчёта. Модификаторы, итоговые бонусы, DC и remaining вычислять при отображении. При нехватке входных данных возвращать `null`/«не настроено», а не догадки.
- **Manual priority.** Legacy/manual значения не пересчитывать автоматически. Computed mode включается только явным выбором и хранит свои входы (`abilitySource`, `proficient`, `additionalBonus`, `calculationMode`).
- **Source tracking.** Любой автоматически добавленный эффект обязан иметь источник и детерминированный ID. Повторное применение должно быть идемпотентным; смена race/class/background удаляет только собственный source, не manual и не чужие sources.
- **Коллекции.** Prepared spell IDs очищаются при удалении spell; creation equipment заменяет только ранее созданные creation items; пользовательские предметы и старые записи без `source` сохраняются.
- **Валидация.** Проверять IDs, schemaVersion, диапазоны и принадлежность ruleset до применения эффекта. Ошибку загрузки показывать пользователю; не восстанавливать повреждённую запись фиктивным персонажем.
- **Сохранение.** Один общий Save обновляет канонический snapshot. Ошибка сохранения не удаляет draft; статус «сохранено» показывать только после успешной записи.

## 4. Правила UI

### Компоненты и состояние

- `CharacterSheetPage`/composable координирует вкладки, draft и сохранение; крупные блоки отвечают только за свой раздел.
- Компонент не знает о storage/API и не содержит доменных формул. Обмен — через typed props/events.
- Большой блок identity, сведения о персонаже и подтверждения открывать существующим modal-контейнером. Modal должен иметь понятное закрытие, возврат фокуса и управление клавиатурой.
- Wizard создания остаётся в корневом приложении. Его preview читает локальное состояние wizard и не сохраняется отдельно; применение использует тот же `CharacterCreationPayload` и общий save flow.
- Статус должен быть понятен без цвета: текст, `aria-live`, visible label, `focus-visible`, selected/disabled/error state.

### Responsive

- Целевые ширины: 1440, 1024, 430 и 375 px. На mobile не должно быть горизонтального overflow страницы.
- Сетки переходят в одну колонку, вкладки прокручиваются внутри собственной полосы, действия остаются доступными, touch targets не уменьшаются до нечитаемых размеров.
- Длинные русские подписи, badges, source text и итоговые бонусы должны переноситься или занимать заранее закреплённую область. Проверять collapsed и expanded состояния.
- `prefers-reduced-motion` уважать; декоративный слой не должен перекрывать поля и менять модель данных.

### Assets

- Хранить пользовательские изображения в `public/images/...`, а не в `src` и не как большие data URL.
- Использовать явное mapping `id → path`; не привязывать классы к случайному порядку файлов.
- Для class portraits хранить gender variants отдельно (`male`/`female` или эквивалентный явный ключ), выбирать вариант по выбранному полу и иметь fallback для старого персонажа/отсутствующего файла.
- Единый контейнер класса: desktop 128×128, mobile 96×96, `object-fit: contain`, сохранение пропорций и прозрачности. Состояния `default/hover/selected/mobile` должны задаваться CSS-классами.
- Проверять alt-текст, загрузку отсутствующего asset и визуальное выравнивание рядом с названием класса в wizard и header.

## 5. Правила для AI-агента

1. Перед изменением прочитать `AGENTS.md`, релевантные архитектурные документы, EV/CR отчёты, текущие типы/adapter/tests и историю связанных коммитов.
2. Зафиксировать цель, границы и короткий план. Если задача просит только документ — не менять код; если просит только UI — не трогать migration/backend.
3. Учитывать незакоммиченные файлы пользователя. Не делать reset, удаление, destructive migration, database operation или массовое форматирование без прямого запроса.
4. Изменять минимальный набор файлов и сохранять существующие контракты. Не расширять scope «на будущее» и не маскировать ошибки через `any`, отключение TypeScript или mock-defaults.
5. После реализации запускать уместные typecheck, тесты, build и `git diff --check`; для UI добавлять browser/viewport smoke, если он доступен. В отчёте явно указывать, что запускалось, а что недоступно.
6. Для каждой новой модели добавлять тесты на lookup/validation, сохранение, adapter round-trip, reload и совместимость старого payload. Для migration отдельно проверять idempotency, unknown fields и исходные keys.
7. В финальном отчёте перечислять изменённые файлы, причину, проверки и остаточные ограничения. Не заявлять о проверке, которой не было.
8. Если пользователь просит остановиться после артефакта, после его создания не выполнять дополнительные изменения, коммиты, публикации или «улучшения».

## 6. Правила для будущего D&D-расширения

### Classes

- Класс имеет стабильный `id`, `ruleset`, display metadata, hit die, primary abilities, saving throws и ссылки на features/equipment/spell progression.
- Иконка и портреты — optional metadata; отсутствие icon не должно ломать старые классы. Gender variant выбирается presentation-слоем, а `class` в Character остаётся совместимым ID/строкой.
- Применение класса пересобирает только `class` source: не стирает manual/race/background, не удваивает bonuses и снимает spellcasting для non-caster явно.

### Spells

- Каталог использует стабильные spell IDs и tags (`ruleset`, level, classes, school). Character хранит ссылки `knownSpellIds`/`preparedSpellIds`; custom/legacy запись хранится embedded и не теряется.
- Prepared IDs должны ссылаться на известные записи; удаление spell очищает зависимые ссылки. DC, attack bonus и slots remaining — derived.
- Не добавлять автоподбор и полный spell rules engine вместе с простым UI-каталогом; сначала определить контракт и migration.

### Feats

- Feat имеет стабильный ID, source, ruleset, prerequisites и явные choice payloads. Выборы нельзя кодировать в свободной display-строке.
- Применение feat добавляет отслеживаемый source/effect и не перезаписывает raw score или manual bonus без явного правила. Повторное применение должно быть запрещено или идемпотентно по ID.

### Progression

- Level-up хранит выбранные class levels, feature IDs и choice IDs; повторное открытие уровня не создаёт дубликаты.
- Проверять диапазон уровня, class/ruleset compatibility и prerequisites до записи. Milestone, ASI и feat choice должны быть отдельными шагами с понятным pending state.
- Не вычислять progression из одной display-строки класса и не смешивать class source с background/race source.

### Effects

- Эффект описывать типизированной записью с `source`, `effectId`, входами и обратимостью. Применение должно быть детерминированным и повторяемым.
- Derived effect показывать через domain helper; сохранять только source и настройки, а не дублировать итог.
- Неизвестные effects сохранять для совместимости. Перед массовым применением показывать preview, а правила, которые меняют несколько разделов, покрывать domain и adapter tests.

## Минимальный критерий готовности

Изменение готово, если оно укладывается в текущую архитектуру, не теряет старые данные, имеет явный source/ID и owner состояния, проверено на нужных viewports и сохранении/reload, а отчёт честно фиксирует проверки и ограничения.
