# DND5V — восстановление функциональности и совместимости

Дата: 2026-11-22

## Причина расхождения

Потеря в основной линии подтверждена. Commit `409733d` удалил архивированные модули, прежний `src/api/characterSheetAdapter.ts` и `CharacterSheetView`, после чего приложение перешло на упрощённую одиночную модель. Commit `e9259d1` отдельно удалил `RestActions.vue`; `90cec0f` удалил 28 файлов старого тестового набора. Исторические файлы и указанные ориентиры проверены по локальной Git-истории.

Старый адаптер преобразовывал доменный Character v3 в представление `CharacterSheetView`. Восстановленный слой не возвращает старую архитектуру целиком: он проецирует старые записи в текущую модель, а полный исходный объект оставляет доступным для восстановления и экспорта.

## Хранение и безопасный перенос

Распознанные ключи:

- текущая одиночная запись: `nastolka:character-sheet`;
- историческая коллекция персонажей: `nastolka:character-sheet:<id>`, `nastolka:character-sheet:index`, `nastolka:character-sheet:active`;
- исторические версии по ключу: `nastolka:character-sheet:v1:<id>`, `:v2:<id>`, `:v3:<id>`;
- старый отдельный НПС: `nastolka:monster-sheet`;
- новые канонические записи: `nastolka:characters:v1:<id>` и `nastolka:npcs:v1:<id>`, с отдельными индексами и активными ID.

Порядок переноса: сначала прочитать и проверить все исходные записи; затем построить записи текущей модели и выявить повреждения/коллизии ID; только после этого записывать новые канонические копии и указатель активного листа. Исходные ключи никогда не удаляются. Повторный запуск идемпотентен. Для v1/v2/v3 без `schemaVersion` версия берётся из проверенного исторического ключа. Конфликтные, повреждённые и неподдерживаемые записи остаются на исходных ключах и сопровождаются сообщением; пустой персонаж вместо них не создаётся.

Скрытые для текущего редактора поля сохраняются в исходной записи, доступной через `sourceRecord` и экспорт. Редактируемая проекция не претендует на изменение полей, которых нет в текущей модели.

Экспорт включает текущую модель и исходную запись. Импорт проверяет JSON, размер, ID и структуру до записи. При режиме добавления совпадающий ID получает новый; при замене меняется только указанный активный персонаж. НПС хранятся в отдельной коллекции. Многострочный импорт откатывает выполненные записи при ошибке хранилища. Удаление исторической записи использует tombstone, оставляя исходный ключ доступным для восстановления.

## Восстановленные возможности

| Область | Результат |
| --- | --- |
| Персонажи | Список и активный ID в совместимом слое; создание, выбор, копирование, удаление; reload. |
| НПС | Отдельная коллекция, активный НПС, создание/копирование/удаление; преобразование из бестиария создаёт независимую копию. |
| Импорт/экспорт | Один персонаж, пакет персонажей и НПС; preview, добавление/замена, обработка коллизий, сохранение неизвестных полей исходной записи. |
| Отдых и ресурсы | Короткий/длительный отдых и spell slots; редакция правил хранится как `2014`/`2024`. Восстановление костей хитов длительным отдыхом: половина при 2014, все при 2024. |
| Атаки и кости | Формулы, d4–d100, изображения, результат, история, Dice Roller. |
| Initiative Tracker | Участники, сортировка, активный ход и следующий раунд. |
| Бестиарий/столкновения | Локальный нейтральный набор, независимая копия в НПС, сохранение участников и хода столкновения в данных персонажа. |

Создание персонажа, ручное редактирование листа, предметы, атаки, заклинания, навыки и черты остаются подключены к текущей модели и её сохранению. Экспериментальные исходники сохранены; progression UI не включался.

## Публичный и внутренний режимы

- Публичная сборка показывает один активный обычный лист. Она загружает и сохраняет его через совместимый адаптер; менеджер, НПС и импорт/экспорт в пользовательском интерфейсе скрыты.
- Внутренний менеджер доступен только в режиме разработки при `VITE_ENABLE_CHARACTER_MANAGER=true`; отдельная коллекция НПС и перенос требуют своих флагов `VITE_ENABLE_NPC_COLLECTION=true` и `VITE_ENABLE_CHARACTER_TRANSFER=true`.
- Бестиарий, планировщик и компоненты включаются локально флагами `VITE_ENABLE_BESTIARY`, `VITE_ENABLE_ENCOUNTER_PLANNER`, `VITE_ENABLE_COMPONENTS`. В production вкладки исключены условием `!import.meta.env.PROD`, даже если сборка тестово выполнена с флагами `true`.
- `.env.example` содержит внутренние локальные значения `true`. GitHub Pages собирается с флагами `false`; в проверочной production-сборке с флагами `true` ограничения также остались включены.
- Router в приложении отсутствует, поэтому прямых маршрутов к скрытым разделам нет.

## Git и публикация

До восстановления ветки `feature/nastolka-demo-modules`, `main` и `origin/main` совпадали на `424261a`; `origin/gh-pages` был `98e9fbb`. После `git fetch origin --prune` feature и main по-прежнему совпадают с указанным commit; независимых удалённых коммитов для слияния нет. Рабочие изменения ещё не опубликованы.

Публикация в `main` и Pages будет выполнена после фиксации и повторной проверки результата. Итоговые commit hash и remote HTTP-проверка будут добавлены сюда после публикации.

## Ограничения

- Browser automation проверяет оба локальных режима; сетевой журнал запросов браузера недоступен.
- Работа с неизвестными legacy-полями производится через сохранённый исходный объект: интерфейс не редактирует их как типизированные текущие поля.
- Новая функция авторизации/облачной синхронизации не добавлялась; коллекции локальны для origin браузера.
